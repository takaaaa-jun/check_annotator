# カテゴリDBの実MySQL検証結果

## 結論

2026年11月2日（日本時間）、隔離した実MySQL 8.0.44・8.4.7の両方でカテゴリ投入コマンドの動作を確認した。
各バージョンで36テストが成功。学内サーバーへの接続・変更は行っていない。

## 実行環境と結果

| 項目 | 内容 |
| --- | --- |
| OS | Windows |
| Python | 3.12.14 |
| SQLAlchemy | 2.1.6 |
| PyMySQL | 1.2.3 |
| pytest | 9.2.0 |
| MySQL 8.0.44 | 127.0.0.1:13317、36 passed in 28.97s |
| MySQL 8.4.7 | 127.0.0.1:13316、36 passed in 28.94s |
| 投入元JSONのSHA256 | `17d5ec7c262c013201daa9b3b64839825fa54450c4042c4d6ef943da92323587` |

MySQLは公式ZIP配布を作業フォルダー内に展開し、サービス登録せずに起動した。
各サーバーはループバックのみで待ち受け、専用の空DBを使用した。
検証終了後に一時MySQLを停止した。

## 確認した内容

`tests/test_categories_mysql.py`の4テストを実MySQLに対して実行した。
通常の検証32テストと合わせ、各バージョンで36件成功した。

| 検証 | 結果 |
| --- | --- |
| `--apply --create-schema`で10テーブルを新規作成・データ登録 | 成功 |
| 配布用`006_create_categories.sql`を適用してから`--apply` | 成功 |
| 元カテゴリ256件、メイン分類41件、対応41件 | 一致 |
| 同一JSONを再投入 | 行・ID・日時・テーブル構造が変わらない |
| 作成済みDBへ`--create-schema`を再指定 | 変更せず拒否 |
| `--check-db` | 10/10を報告、データ変更なし |
| 先に新規行をINSERT後、既存行との競合を検出 | 今回のデータ変更を全てロールバック |
| 未対応の元IDへ分類を後から追加 | 256件を保持し、分類・対応が各42件になる |
| category6がNULLの同一分類を二重登録 | DBが拒否 |
| 存在しないマスタIDへの外部キー参照 | DBが拒否 |
| 同じ元カテゴリに有効な対応を重複登録 | DBが拒否 |
| 対応先階層に7を直接INSERT | DBのCHECKが拒否（3819） |
| 旧対応を論理削除後、新しい有効対応を追加 | 成功、旧対応は保持 |
| 別接続が投入ロックを保持中にコマンド実行 | テーブル作成前に拒否 |
| コマンド正常終了後のロック解放 | 別接続から取得できる |
| 既存6テーブルの保持 | 定義・全行が投入前後で一致 |

既存6テーブルは実際のSQL 001〜005で作成した。
roles・users・statesの初期値に加えて、groups・tasks・commentsにも検証行を登録して比較した。
ロールバックではMySQLの採番カウンターは戻らないため、次回採番値だけを構造比較から除いた。
既存行の主キーや内容は変更されていない。

## 発見して修正した不具合

実MySQLではVARCHARやTEXTの反映型に`COLLATE utf8mb4_unicode_ci`が付く。
従来の型比較では、この付加情報によって正しいテーブルを型不一致と判定していた。
基本型の比較から照合順序表記を除外し、テーブルの照合順序を別途確認する処理に修正した。
修正後、スキーマ作成からデータ投入まで成功した。
